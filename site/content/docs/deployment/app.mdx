Two Railway services serve two hostnames from one repository.

| Host | Service | Config | Health check |
| --- | --- | --- | --- |
| `studio.vukem.dev` | `studio` (documentation) | `railway.toml`, `Dockerfile` | `/docs/introduction` |
| `app.studio.vukem.dev` | `studio-app` (the app) | `railway.app.toml`, `Dockerfile.app` | `/up` |

## Image

`Dockerfile.app` builds the Vite assets and a static Go binary. The runtime image adds `ffmpeg`, a font, and only the `SKILL.md` and `SKILL.en.md` files of `.agents/skills/`. It runs as a non-root user.

The image sets `QUEUE_CONNECTION=database`, so `serve` runs the render worker beside the web server.

## Before traffic

Railway reads only the root `railway.toml`, and it applies to both services, so it holds just the shared builder and restart policy. Each service picks its image with a variable: `RAILWAY_DOCKERFILE_PATH=Dockerfile` on `studio` and `RAILWAY_DOCKERFILE_PATH=Dockerfile.app` on `studio-app`. Set the rest of `railway.app.toml` in the `studio-app` service settings.

The start command is `/bin/sh -c "/app/app migrate && exec /app/app"`. The database is a SQLite file on the volume mounted at `/app/storage`, and Railway mounts volumes only for the running container, never for a pre-deploy command. Migrating at start runs against the real file before the server listens; a failed migration exits and fails the deploy. Keep the service at one replica.

Two more settings come from how Railway runs the container. Its volumes are owned by root while the image runs as uid `10001`, so the service sets `RAILWAY_RUN_UID=0` and the start command first gives `/app/storage` to that uid (the mount point, then only the entries with another owner, never following links), then runs `migrate` and the server as `app`: `/bin/sh -c "chown 10001:10001 /app/storage && find /app/storage -xdev ! -user 10001 -exec chown -h 10001:10001 {} + && exec su app -s /bin/sh -c '/app/app migrate && exec /app/app'"`. The custom domain targets port 3000, so the service also sets `PORT=3000`. The image sets `QUEUE_TABLE=queue_jobs` and `QUEUE_FAILED_TABLE=queue_failed_jobs`, because the app already owns a `jobs` table for render jobs.

## Variables

Set these on the `studio-app` service. Values are never committed.

| Variable | Notes |
| --- | --- |
| `APP_KEY` | Generate once. Keep it stable |
| `APP_URL` | `https://app.studio.vukem.dev` |
| `DATABASE_URL` | PostgreSQL URL from the Railway database, or a SQLite file on the volume |
| `SOCIAL_GOOGLE_CLIENT_ID` | From the Google OAuth client |
| `SOCIAL_GOOGLE_CLIENT_SECRET` | From the Google OAuth client |
| `ANTHROPIC_API_KEY` | Claude models |
| `OPENAI_API_KEY` | Optional, OpenAI models |
| `STUDIO_MODEL` | Optional. Defaults to `claude-sonnet-5-5` when the Anthropic key is set |
| `STUDIO_MAX_JOBS_PER_DAY` | Optional |
| `STUDIO_MAX_JOB_COST_CENTS` | Optional |
| `STUDIO_MAX_OUTPUT_TOKENS` | Optional |

The image already sets `APP_ENV`, `HOST`, `PORT`, `QUEUE_CONNECTION`, and `STUDIO_STORAGE`. See [Configuration](/docs/configuration) for the rest.

## Volume

Mount a Railway volume at `/app/storage`. It holds the job folders in `/app/storage/renders`, and the SQLite file when `DATABASE_URL` points there. Without a volume, files vanish on every deploy.

## Google OAuth

In the Google Cloud console, add these **Authorized redirect URIs** to the OAuth client:

| Environment | Redirect URI |
| --- | --- |
| Production | `https://app.studio.vukem.dev/auth/google/callback` |
| Local | `http://localhost:3000/auth/google/callback` |

The callback is `APP_URL` plus `/auth/google/callback`. A mismatch shows Google's `redirect_uri_mismatch` page, so check `APP_URL` first.
